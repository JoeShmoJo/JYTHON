RTS baseline and augmentation: process and file reference

Current implementation, 10 November 2026. Start with the operator SOP. This reference describes the current four-button menu and compact-run backend, rather than the earlier experimental menu layouts. It documents the project implementation; an older installed script set may behave differently. The data I/O audit describes the archive change.

Locations and terminology

Examples below use these roots; substitute the paths shown by your selected forecast.

The forecast alternative (for example ConSeason), ResSim model alternative (for example Con_Season), and output run code (for example C0) are related but not interchangeable names. The menu derives context from the selected RTS run. Computed ensemble F-parts are normally C:<six-digit-member>|<run-code>. Dates and timezone come from the forecast runtime window, not standalone CONFIG.SIM_NAME. HEC 2400 denotes the following midnight; keep the displayed HEC date/time convention when checking the window.

A baseline is an accepted unaugmented result, not simply a named configuration. A reusable baseline configuration is a portable set of scripted-rule settings. A reusable augmentation configuration is a reservoir table plus calculation settings. A scheme is that augmentation configuration resolved into releases for one particular baseline, window and ensemble. An archived result is the completed simulation after loading a scheme. Saving a configuration does not compute or accept results. “Commit” here means activating prepared releases.

Initial extraction

Trigger: Initial Extract. Input: selected RTS context, installed downloader configuration/mappings in EP\CONFIG.py and the downloader modules, network data services, and any existing live inputs used to seed the staged file.

For Extract archived forecast inputs, the archive reader rts_archive.py replaces the live RFC downloader below. It checks one common issue, actual member years, full daily coverage and the selected leap-day policy before network requests. The archive dialog supplies the folder, requested years and OSI source. Both paths use the same staged loading/promotion safeguards. See archived forecast details.

run_extraction.py runs these bundled scripts in order:

  1. RFC_Downloader_Module.py: downloads current NWRFC ensembles, processes flows, and writes forecast-mode ensemble DSS records.
  2. CWMS_Downloader_Module.py: obtains required lookback elevations and configured observations/other groups from CWMS; writes DSS records.
  3. Dummy_0_and_WY_Abundant_Module.py: writes the zero dummy and abundant-water-year inputs.
  4. OSI_Ensemble_Year.py: creates the configured OSI member data.
  5. write_rule_curves.py: writes configured rule-curve records from the annual CSV.
  6. write_ensemble_shared_inputs.py: makes required shared inputs available under ensemble paths used by ResSim.

The menu promotes only the newly completed extraction matching this invocation's context and verifies its hash. Partial folders remain for diagnosis but are not substituted for a completed extract. The standalone extraction launcher RTS_FORECAST_EXTRACT.py has separate plan/test behavior; its test-copy-only messages do not describe the menu's subsequent promotion step.

The RFC downloader supplies the current issue, not arbitrary historical forecasts. Requested windows must fit actual data availability. Historical RFC archive loading is not part of this SOP. CWMS lookback timestamps must cover the required window; missing required data is not filled or extrapolated. Forecast synthetic percentile members are 3000/3001/3002 and OSI is 3003 in the current extraction conventions; which members compute depends on the model alternative and available inputs. Members below 3000 and at/above 3000 are kept separate in plotting. Do not infer that every downloaded member was computed successfully.

Unused IRRM and Deep Drawdown reservoirs have inactive null configuration slots. No native rule binding is added. Off or incomplete entries impose no additional release requirement, even with the switch on. The browser and resolved operating_status distinguish Off, Not configured and On. The backend excludes off/incomplete Deep Drawdown rows from runtime CSVs and masks off/incomplete IRRM targets inactive. Existing values and older snapshots are preserved.

Save does not apply. Apply disables augmentation and records a pending unaugmented compute; settings take effect at the next initialization, not halfway through a running simulation. Acceptance checks initialization receipts for the configured members, but receipts do not prove successful simulation completion. Applying creates new forecast-scoped files; it does not overwrite the standalone source CSV configurations. Shared reusable libraries live under WS, so preserve them across watershed reimports. Directly editing source CSVs is outside this editor's isolation behavior.

Compute, acceptance and baseline identity

Live simulation outputs are written by ResSim into its configured DSS, normally F\forecast.dss. Compute logs are native application artifacts, not produced by the workflow's Python tasks. Native ensemble-through-ResSim examples write F\rss\C0.log, worker C0*.log/.log.tmp and C0.rssrun; CWMS-orchestrated ensemble examples can write F\EnsembleRuns\<member>\C0.log. Locations depend on the compute path. The RTS-launched ResSim server log has appeared at %LOCALAPPDATA%\Temp\1\logs\ResSimServer.log; check its timestamp before relying on that session-specific example. A new log ending in successful completion matters more than an old DSS record's presence or a progress bar showing 100%.

Trigger: Yes in the completion question opened by Augmentation Configuration, Plot Results, or Process and Load Releases. With augmentation inactive, acceptance saves/compares an unaugmented baseline. With augmentation active, it captures a result under that scheme. A loaded scheme is not a completed result.

Baseline equality compares computed reservoir pool elevation and outflow only, for the run code and archived members: timestamps, values, units and type, with no numerical tolerance. It ignores DSS layout/block naming. It does not compare operation-set files, configuration names, river flows, water-year inputs or every other variable. Missing previously archived pool series causes rejection rather than silently accepting an incomplete baseline.

Changed compared results create a new immutable baseline ID; old augmented results retain their original data and pairing, labelled Previous baseline. Identical compared results keep the existing baseline and its archive. A newly applied configuration can therefore be accepted with separate provenance while the baseline ID stays unchanged. Configuration/script changes alone do not necessarily create a new result baseline.

Rebuild after array damageNo: primary data must be recovered from a backupDisposable cache can rebuild from intact archived DSS

New acceptance captures selected full time series, not peak summaries. It scans the catalog and reads selected physical date blocks once, retaining pool outputs, plot control-point flows, reservoir storage/inflows needed by augmentation, Combined Min Trib requirements and water-year values for the run. It excludes unrelated runs, powerhouse/tailwater/diversion/return outputs, unrelated reaches, and DSS rule-curve searches. The scope includes all cataloged members for the accepted run code, not a certified list of only the latest successful members.

series.npz is compressed NumPy data loaded without pickle. run-archive.json records logical DSS paths, timestamps' array references, units/types/timezones, array checksum, content hash and source-file signature. Existing APIs may still refer internally to B\forecast.dss as a logical source locator; a new compact archive does not physically contain that DSS file. Plots and preparation use the array reader instead. Corrupt primary data fails verification; current live outputs are never silently substituted for archived results.

Capture checks live file size and timestamps around the read. This detects normal concurrent writes, not adversarial changes with preserved metadata. Finish compute before acceptance. Unchanged legacy baselines may remain DSS-backed; existing archives are neither converted nor deleted automatically.

Augmentation inputs, preparation, activation and results

The augmentation editor starts from WS\scripts\externalSVs\MinFlowSalemAlbanyConfig.csv. This reservoir table includes aliases, participation, conservation elevations/storage, summer buffer elevations, maximum release and travel time. The current calculation uses participation, storage floors, release limits and travel times; retained elevation/buffer fields do not imply additional implemented logic. Current participation restrictions require Lookout Point and combine Hills Creek with it, with identical Salem/Albany support flags.

Additional maintained inputs are WS\scripts\externalSVs\MinFlowSalem_2008BiOp.csv and MinFlowAlbany_2008BiOp.csv, plus EP\median_remaining_by_day.pkl and EP\MainstemAugmentation.py. The target tables provide mainstem requirements; the pickle provides median remaining-inflow data. Do not replace the latter with an untrusted pickle. Their exact copies/hashes are saved with each scheme.

Baseline arrays supply storage, inflow/outflow, Combined Min Trib release requirements, Salem/Albany flows, and water-year values. The Green Peter minimum uses the saved Green Peter Combined Min Trib output, which already accounts for the downstream Foster target/mass balance, rather than substituting Foster's minimum directly.

Short forecast days is the calculation's short-horizon setting (default 10), not the total forecast length or ensemble count. The season year identifies the covered April–October augmentation season, not the historical member year. The menu offers seasons based on saved output coverage and caps the end at the earlier of October 31 and common coverage. Preparation also requires the travel- time lead-in and complete required daily inputs. It does not invent missing dates.

Water-year modes differ: storage-maf expects physical MAF-labelled values; fixed-abundant explicitly treats the input as the constant category 4, even if ResSim exports a storage unit label. The latter rejects 0, other values and missing samples. It must not silently reinterpret or replace an arbitrary input with 4.

Processing validates the saved baseline and snapshots configuration, writes only prepared releases into augmentation.dss, then verifies and loads manifest-listed records into a staged live DSS. Whole-file staging is retained to avoid partially changing the live input file. The old live DSS is retained by rename; a caught promotion failure restores it. An interruption between renames may require manual restoration from that backup. Loading writes the active marker; it never computes.

A scheme manifest's prepared-not-computed status describes preparation and is not rewritten to certify model success. capture.json records the separately accepted result, time, archive identity and baseline pairing. Operator-confirmed compute status is not independent log verification. Reaccepting unchanged compact result content under the same scheme/baseline reuses the saved result. An earlier baseline's scheme cannot be activated as a current-baseline scheme; its archived results remain available for plotting.

Matching historical members are paired for comparisons; synthetic traces stay separate. Matching baseline IDs make a baseline/augmentation comparison interpretable. Cross-baseline comparisons are explicitly labelled as containing baseline changes.

Plotting uses saved arrays or legacy caches, not current live simulation results. Baseline-only plots have no augmentation overlay. Requirement traces can vary by ensemble member; identical traces are displayed once, differing requirements have a range and individually selectable traces. The annual CSV supplies available rule curves without searching ResSim/CWMS DSS records for longer coverage. Dexter and Big Cliff have no curve from this CSV.

Older comparison CLI plots can also live under R\plots-<token>; the current chooser creates output_plots\saved-runs-*. Earlier plot files remain. Their labels reflect the status when generated; the chooser and new plots use current baseline status.

Delete Selected Augmented Result confirms deletion of that result and plots that include it. It retains its scheme's configuration/prepared releases, baselines, other results, and action history. Old/failed extraction folders and full live- DSS recovery backups are not automatically purged. Baselines have no delete button. Do not remove primary compact arrays under the assumption they are caches.

A workflow task lock prevents overlapping backend menu tasks; it does not stop someone starting a native compute independently. Never delete a lock until its recorded process has stopped and the partial task has been inspected.

The menu includes live extraction, archive compatibility/extraction, baseline and augmentation configuration, Model Check and plots; Reset Baseline is not a normal menu action. Older CLI/backend reset/load commands remain for compatibility and are not required for the normal configuration-driven SOP. No archived operation-set file is restored by applying a baseline configuration. The imported alternative and rule bindings still need to be correct.

Use the shared OPEN_WORKFLOW.py opener or the separate local LAUNCH_WORKFLOW_GUI shortcut. Never replace the GUI implementation RTS_WORKFLOW_MENU.py with a launcher stub. To update an imported copy, close the workflow GUI and copy the complete updated scripts tree, retaining RTSPython. The GUI displays the backend path and checks for matching archive functionality. No mode installer or application JAR modification is part of this procedure.

Do not assume an input-only change was captured; a fresh forecast is the clean workaround pending a dedicated fix. Do not force a result change by altering unrelated operating settings.

The separate PostProcess_CSV cleanup script is not the workflow archive producer. Its code is the model's existing cleanup script, rather than one of the menu's ExternalPython tasks. Outputs are placed beside the model's configured DSS output:

PostProcess outputCreator / contentsWorkflow consumer
PeakExtract_<alternative>.csvEnsemble cleanup branch; appended member IDs, timestamps and peak flows/elevationsNot used as full-series baseline or augmentation input

This workflow needs full daily member series for augmentation and plots, so peak CSVs cannot replace its compact archives. Direct per-member memory export and reduced native DSS output remain separate future work.

Archive directories preserve results/configuration provenance, not an entire executable, environment, all native operation sets or a fully portable watershed. For a study handoff, retain the needed forecast/inputs/model, applied settings, schemes with their referenced baselines, result and plot archives, plus installed code/environment information. Reusable configuration libraries and raw RFC copies live under the shared watershed rather than under each forecast; include them separately when needed. Do not claim a result can be recomputed from series.npz and a configuration JSON alone.
